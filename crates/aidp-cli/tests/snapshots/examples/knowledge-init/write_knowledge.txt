## Project knowledge — you are writing the project's knowledge base

Your output directory `./.aidp/knowledge` IS the project knowledge base: one curated set of notes describing the **service itself**, shared by every ticket and every run, and read as the primary context by every later pipeline. It is not a run folder and nothing here is disposable.

Rules:
1. **List and read what is already there first.** Existing notes are the baseline.
2. **Update in place.** Correct what is now false, fill what is missing, delete what no longer exists. Never add a parallel document restating a note that already exists, and never append a dated section — a reader must find one current answer, not a changelog.
3. **Only durable facts.** Architecture, components, events in/out, domain model, data stores, integrations, invariants, gotchas. No ticket narrative, no run commentary, no `plan` for the current work — that belongs in this run's folder.
4. **Write for an AI agent starting cold on this service.** State what it must know to work here safely, with file paths and names it can grep for.
5. Notes named `_*.md` are generated by `aidp` — never write or edit those.

This stage owns the **transverse layer only**: the notes at the base root. The per-feature notes under `./.aidp/knowledge/Features` belong to a different stage — read them if useful, do not write them here.

## Reply envelope

Your FINAL answer is the reply envelope (it is schema-validated by the runtime — return it directly, do NOT write `reply.md`). Fields:
- `status`: one of `completed` | `blocked` | `needs_review` | `failed`.
- `summary`: one short paragraph (no artifact bodies inlined).
- `outputs`: map of declared output name → absolute file path (string values only).
- `signals`: object of booleans/counters the orchestrator branches on. If you are a reviewer, you MUST set `signals.has_blocking_findings` (boolean). Optionally add `findings_count`, `confidence`, etc. `signals.escalations`: optional array of `{id, decision, reason}` for items that need a human without blocking the run.
- `assumptions`: optional array of `{choice, reason, rejected_alternative?, question_id?, question?}` for each choice taken in place of a question.
- `follow_ups`: optional array of strings. `ask_user_questions`: array of `{id, question, answer?, options?, recommended?}` (`options` an array of strings, `recommended` a string) — leave it EMPTY unless a real blocker stops you. Decide open points yourself and record the decision and its rationale in `follow_ups` or your artifact. An entry with a non-empty `answer` on a `completed` stage is only informational; one with no `answer` pauses the whole run for a human. `scope_violations`: array of blocked paths. `metrics`: optional `{tool_calls, duration_ms, tokens_used}`.
