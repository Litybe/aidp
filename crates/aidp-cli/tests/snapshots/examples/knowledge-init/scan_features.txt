## Inputs (paths or values)

- `knowledge_context`: ./.aidp/pipelines/knowledge-init/knowledge__knowledge_read/knowledge_context.md
- `path`: .
- `task`: Inventory the BUSINESS features this service implements and write features.md plus features.json. A feature is a capability a product person would name and a user or another service would notice — "temporary self-exclusion", "deposit limits", "payment cheat scoring" — not a technical layer ("repositories", "the SNS publisher") and not a single function. Derive them from the entry points, the use cases / commands, the events published, the feature flags and the domain vocabulary, then MERGE what is really one capability seen from two angles. For each feature give: a slug (kebab-case), the business name, the other names it goes by in code, tickets or docs (aliases), the domain/bounded context it belongs to, its entry points, the events it consumes and publishes, the stores it touches, and the files that carry it. Aim for 5 to 20 features: fewer means you stayed at the service level, more means you sliced technical units instead of capabilities. Say in features.md which parts of the code you could NOT attribute to any feature — that gap is more useful than a made-up feature. Then emit `signals.features` as an array of slugs, one per feature you found, ordered most to least important.
